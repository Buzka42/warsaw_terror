- **What we found** (with source URLs)
  - **GnssLogger does log Galileo Nav records — if the chipset delivers them.** Google's GnssLogger Home Tab controls “raw GNSS measurements, GnssStatus, NMEA, navigation messages, sensor data and RINEX logs” via switches, and Log Tab has “Start Log / Stop & Send / Timed Log”. Play Store: https://play.google.com/store/apps/details?id=com.google.android.apps.location.gps.gnsslogger
  - **Log format is fixed and parseable.** Rows are prefixed `Nav` for `GnssNavigationMessage`, with header `# Nav,Svid,Type,Status,MessageId,Sub-messageId,Data(Bytes)`. Doc: https://raw.githubusercontent.com/google/gps-measurement-tools/master/LOGGING_FORMAT.md
  - **Android API specifies Galileo I/NAV as 29 bytes / 228 bits.** `TYPE_GAL_I = 1537` is “Galileo I/NAV message contained in the structure”, and `getData()` says: “For Galileo I/NAV, each page contains 2 page parts, even and odd, with a total of 2x114 = 228 bits … fit into 29 bytes, with MSB first”. API: https://developer.android.com/reference/android/location/GnssNavigationMessage
  - **The SAR field is in that data, but only on E1-B odd pages.** Galileo OS SIS ICD Issue 2.1 — Nov 2023, Table 36 gives odd-part allocation `1 1 16 40 22 2 24 8 6` (Even/Odd, PageType, Data, Reserved1/OSNMA, **SAR 22**, Spare, CRC, SSP/Reserved2, Tail), and states “SAR data (22 bits) composed of SAR RLM data on E1-B only”. ICD: https://srvdc10.gsc-europa.eu/sites/default/files/sites/all/files/Galileo_OS_SIS_ICD_v2.1.pdf
  - **Derived bit offset (my calculation from the two primary sources above):** Android concatenates even (114 bits, tail excluded) then odd (114 bits). SAR starts at 114 + (1+1+16+40) = **bit 172, length 22, bits 172–193 inclusive, 0-indexed MSB-first**, in the 29-byte `Data(Bytes)` field. This is not printed as such in either source — you must implement and CRC-validate it.
  - **CRITICAL GAP: `Nav` alone does NOT establish E1-B.** The `GnssNavigationMessage` API exposes only Svid/Type/Status/MessageId/SubmessageId/Data — no carrier/frequency field. `TYPE_GAL_I` covers I/NAV, which Galileo transmits on **both E1-B and E5b-I**; the ICD Table 36 header explicitly contrasts E5b-I vs E1-B layouts, and on E5b-I the corresponding CRC field list differs (Reserved1, no SAR/OSNMA). Extracting bits 172–193 from an E5b-I record would give you non-SAR bits. **E1-B identity must be inferred from `Raw`/`Status` rows in the same log** (CarrierFrequencyHz and CodeType — `CODE_TYPE_B` = “GALILEO E1B”, `CODE_TYPE_I` includes “GALILEO E5b I”), and that is inference, not proof.
  - **Support is OPTIONAL and chipset-dependent — there is no official phone list.** Android docs: raw GNSS is mandatory on Android 10+ (API 29), and on Android 9 and lower only for hardware year 2016+; but “Navigation message” support is listed as optional and chipset-varying. Android docs: https://developer.android.com/develop/sensors-and-location/sensors/gnss
  - **CONFLICTS (blunt, as instructed):**
    1. Official spec says I/NAV Data = 29 bytes, but Samsung Galaxy A50/A51 users reported GnssLogger/GPSTest `TYPE_GAL_I` records with **32 bytes**, MessageId up to 30 (spec: 1–24), SubmessageId values like 59/19 (spec: word type 1–10+). Forum: https://forum.developer.samsung.com/t/galaxy-a50-a51-models-provide-inconsistent-galileo-data/8972
    2. A 2019 EUSPA/Airbus OS-NMA smartphone study (old, for context only) claimed Qualcomm-chipset phones “do not provide navigation messages” while Broadcom ones did, and that delivery often stopped after ~300 s unless duty cycling was handled. **Do not treat this 2019 claim as current truth for 2026 chipsets** — it proves delivery is firmware/chipset-specific, not universal.
    3. GnssLogger minimum Android version is reported inconsistently across mirrors (7.0+ designed-for vs 10+ split bundle). Trust only what your installed build reports (see Exact action).
